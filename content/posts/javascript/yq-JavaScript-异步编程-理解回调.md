我们在使用 JavaScript 的时候，经常会遇到大量的回调函数，例如浏览器中使用 setTimeout 来设置定时器，使用 XMLHTTPReqest 去异步的请求数据，Node 中使用 readFile 读取文件。这些操作都需要调用 API 传入回调函数，然后浏览器或者 Node 执行的结果会通过回调函数来触发。

## 1、什么是回调函数

回调函数其实就是人们的一种约定俗成的定义，它具备函数的所有特征，可以有参数和返回值。回调函数区别于普通函数的地方在于它的调用方式，只有当某个函数被作为参数传递给另外一个函数，或者宿主环境，然后该函数在函数内部或者宿主环境中被调用了，即回调函数。

### 1.1、同步回调

```javascript
var myArr = ['joinmouse', 'demo', 'key']
function handlerArray(indexName, index) {
    console.log(index + "." + indexName)
}
myArr.forEach(handlerArray)
```

上面的代码中，数组调用 forEach 的时候，传入了回调函数 handlerArray 作为其参数，在 forEach 方法内部，会遍历 myArray 数组，每遍历一次都会调用一次回调函数 handlerArray。

因为 handlerArray 是 forEach 的参数，而 handlerArray 是在 forEach 函数内部执行，所以这是一个同步回调。

### 1.2、异步回调

异步回调与同步回调函数不同的是，异步回调函数并不是在它执行的函数内部被执行，而是在其他的位置和其他的时间点被执行，比如 setTimeout 代码的例子：

```javascript
function foo() {
    console.log('foo')
}
setTimeout(foo, 1000)
```

这段代码中，我们使用了 setTimeout 函数，setTimeout 的第一个参数 foo 就是一个回调函数，V8 执行 setTimeout 时，会立即返回。等待 3000 毫秒之后，foo 函数才会被 V8 调用，foo 函数并不是在 setTimeout 函数内部被执行的，所以这是一个异步回调。

相信对于同步回调函数的执行时机，我们理解起来比较简单，就是回调函数在执行函数内部被执行，那么异步回调函数在什么时机被执行呢？其实这就需要结合之前一篇博客中写道的浏览器线程架构中的消息队列和事件循环系统来看了。

## 2、UI（渲染）线程宏观架构

早期浏览器的页面运行在一个单独的 UI 线程中，页面需要引入 JavaScript，那么就将 JavaScript 也运行在于页面相同的线程上，这样才能方便的使用 JavaScript 去操作 DOM，所以最开始的时候 JavaScript 就被设计成了运行在 UI 线程中。

所谓 UI 线程，就是运行在窗口的线程，当运行一个窗口的时候，无论该页面是 Windows 上的窗口系统或者 Android 或者 iOS 上的窗口系统，它们都需要处理各种事件，比如触发绘制页面的时间、鼠标点击、触发、放大缩小的事件，也有资源下载、文件读写等等。

在 UI 线程中，当一个事件被触发的时候，例如用户使用鼠标点击了页面，系统需要将该事件交给 UI 线程去处理，在大部分的情况，UI 线程不能立即响应和处理这些事件。因此浏览器内部为 UI 线程提供了消息队列，并将这些待执行的事件添加到消息队列中，然后 UI 线程会不断循环地从消息队列中取出事件、执行事件。我们将 UI 线程每次从消息队列中取出事件，执行事件的过程称为一个任务（宏任务）。

通用 UI 线程架构：

```javascript
// JavaScript 模拟这个过程
function UIMainThread() {
    while(queue.waitForMessage()) {
        Task task = queue.next()
        processNextMessage(task)
    }
}
```

queue 是消息队列，`queue.waitForMessage()` 会同步等待消息队列中的消息到达，没有消息 UI 线程就会被挂起。若消息队列中有消息，则使用 `queue.getNext()` 去取下一个要执行的消息，并交给 processNextMessage 来处理消息。

## 3、异步回调函数的调用时机

通过理解 UI 线程的基础架构模型，我们就很容易的去理解上面异步函数的举例 `setTimeout(foo, 3000)` 的执行时机了。

### 3.1、setTimeout 的调用时机

分析：UI 主线程执行 A 任务的时候调用 `setTimeout(foo, 3000)`，在执行 setTimeout 函数的过程中，宿主会将 foo 函数封装成一个事件，等到 3000ms 后会将其添加到消息队列中，然后 setTimeout 函数执行结束。主线程会不断的从消息队列中取出新的任务，执行新的任务，等待合适的时机，就会取出 setTimeout 设置的 foo 函数回调的任务执行，此时 foo 函数被调用了。

为什么我们说 setTimeout 的执行时间不是精准的，我们也可以从消息队列中来分析下：假设当前系统距离 setTimeout 执行过了 2997ms，此时 UI 线程从任务队列中取去下一个任务执行时间花费 8ms，此刻时间大于 3000ms，取去 setTimeout 中的 foo 函数执行的时候，发现此刻执行时 3005ms 才去执行的，因而我们在写动画的时候不太推荐使用 setTimeout，而是使用 requestAnimationFrame，因为 requestAnimationFrame 的时间是每隔 16.6ms 调用系统自动刷新。

### 3.2、XMLHttpRequest 的调用时机

这里我们以 UI 线程处理下载事件为例，大致可以分为以下几个步骤：

1. UI 线程从消息队列中取出一个任务，分析该任务
2. 分析过程发现是一个下载请求，那么主线程将该任务交给网络线程去执行
3. 网络线程接受到请求后，便会与服务端建立链接，并发出下载请求
4. 网络进程不断地接受服务端传过来的数据
5. 网络线程每次收到数据，将设置的回调函数和返回的数据信息，如大小、字节等等在内存中封装成一个新的事件，将该事件放到消息队列中
6. UI 线程去循环的读消息队列中的事件、如果是下载状态的事件，那么 UI 线程会执行回调函数，我们可以在回调函数内部编写更新下载进度的状态的代码
7. 直到最后接受到下载结束事件，UI 线程会显示该页面下载完成

上面就是 XMLHttpRequest 的回调流程，除了下载之外，JavaScript 中获取系统设备信息、文件读取等都采用了类似的方式去实现。理解 XMLHttpRequest 的回调时机，也就理解了异步 API 的执行流程。

主要参考：李兵老师的《图解 V8》

## 浏览器消息队列和事件循环系统

我们知道浏览器页面的每个渲染进程都有一个主线程，并且主线程非常繁忙，既要处理 DOM，又要计算样式，还要处理布局，同时还需要处理 JavaScript 任何以及各种输入的时间。要让这么多不同类型的任务有条不紊的在主线程中执行，这就需要一个系统来统筹调度这些任务，这个统筹调度系统就是消息队列和事件循环系统。

### 1、单线程处理多个任务

我们先从最简单的场景讲起，比如有如下一系列的任务：

- 任务 1：1+2
- 任务 2：20/5
- 任务 3：7*8
- 任务 4：打印出任务 1、任务 2、任务 3 的运算结果

我们编入如下代码：

```cpp
void MainThread(){
     int num1 = 1+2; // 任务 1
     int num2 = 20/5; // 任务 2
     int num3 = 7*8; // 任务 3
     print("最终计算的值为:%d,%d,%d",num,num2,num3); // 任务 4
 }
```

整个执行的流程如下：并不是所有的任务都是在执行前统一安排好了，有些可能是在线程运行过程中产生的，要想在线程运行过程中，能接收并执行新的任务，就需要采用事件循环机制。

### 2、在线程运行过程中处理新任务

我们可以通过一个 for 循环语句来监听是否有新的任务，代码如下：

```cpp
//GetInput 等待用户从键盘输入一个数字，并返回该输入的数字
int GetInput(){
    int input_number = 0;
    cout<<"请输入一个数:";
    cin>>input_number;
    return input_number;
}
// 主线程
void MainThread() {
    for(;;){
        int first_num = GetInput();
        int second_num = GetInput();
        result_num = first_num + second_num;
        print("最终计算的值为:%d",result_num);
    }
}
```

相对第一版本，引入了循环机制和事件：

- 第一点引入了循环机制，具体实现方式是在线程语句最后添加了一个 for 循环语句，线程会一直循环执行。
- 第二点是引入了事件，可以在线程运行过程中，等待用户输入的数字，等待过程中线程处于暂停状态，一旦接收到用户输入的信息，那么线程会被激活，然后执行相加运算，最后输出结果。

上面我们改进了线程的执行方式，引入了事件循环机制，可以让其在执行过程中接受新的任务。但是上面的任务都是在线程内部的，如果是从其他的线程过来的任务，上面的模型是不可行的。

### 3、处理其他线程发送过来的任务

渲染进程间线程发送任务：上图中我们可以知道渲染的主线程会频繁的去接受来自 IO 线程的一些任务。接收到这些任务之后，渲染进程就需要着手处理，比如接收到资源加载完成的消息后，渲染进程就要着手进行 DOM 解析了；接收到鼠标点击的消息后，渲染主线程就要开始执行相应的 JavaScript 脚本来处理该点击事件。

通常我们会使用消息队列，消息队列是一种数据结构，可以存放要执行的任务。它符合队列"先进先出"的特点，也就是说要添加任务的话，添加到队列的尾部；要取出任务的话，从队列头部去取。

引入消息队列后，我们的模型就如下所示：

1. 添加一个消息队列；
2. IO 线程中产生的新任务添加进消息队列尾部；
3. 渲染主线程会循环地从消息队列头部中读取任务，执行任务。

通过消息队列，我们实现了线程之间的消息通信。

### 4、处理其他进程发送过来的任务

在 Chrome 中跨进程之间的任务也是频繁发生的，那么如何处理其他进程发送过来的任务？

图中我们可以知道渲染进程中会有一个专门的 IO 线程来接受其他进程传入的消息，接受消息之后会将这些消息组装成任务发送给渲染主线程。

### 5、消息队列中的任务类型

现在已经知道页面主线程是如何接收外部任务的了，消息队列中的常见的任务类型如输入事件（鼠标滚动、点击、移动）、微任务、文件读写、WebSocket、JavaScript 定时器等等。

除此之外，消息队列中还包含了很多与页面相关的事件，如 JavaScript 执行、解析 DOM、样式计算、布局计算、CSS 动画等。

以上的这些事件都是在主线程中去执行的，所以在编写 web 程序的时候，需要考虑这些事件占用的时间，避免出现单个任务占用主线程过久的问题。

### 6、页面使用单线程的缺点

通过上面我们已经知道：页面线程所有执行的任务都来自于消息队列。消息队列是"先进先出"的属性，也就是说放入队列中的任务，需要等待前面的任务被执行完，才会被执行。鉴于这个属性，就有如下两个问题需要解决。

#### 6.1 如何处理高优先级的任务

一个典型的场景是监控 DOM 节点的变化情况（节点的插入、删除、修改等动态变化），然后根据这些变化来处理相应的业务逻辑。一个通用的设计是利用 JavaScript 设计一套监听接口，当变化发生时，渲染引擎同步的去调用这些接口，这是一个典型的观察者模式。

但是这个模式的问题在于，当我们的 DOM 变化非常频繁的时候，当每次发生变化的时都去直接调用相应的 JavaScript 接口，那么这个当前的任务执行时间会被拉长，从而导致执行效率的下降。

如果将这些 DOM 变化做成异步的消息事件，添加到消息队列的尾部，那么又会影响到监控的实时性，因为在添加到消息队列的过程中，可能前面就有很多任务在排队了。

总结一下就是，如果 DOM 发生变化，采用同步通知的方式，会影响当前任务的执行效率；如果采用异步方式，又会影响到监控的实时性。

为了兼顾执行效率和监控实时性，就诞生了**微任务**。

通常我们把消息队列中的任务称为宏任务，每个宏任务中都包含了一个微任务队列，在执行宏任务的过程中，如果 DOM 有变化，那么就会将该变化添加到微任务列表中，这样就不会影响到宏任务的继续执行，因此也就解决了执行效率的问题。

宏任务主要功能执行完后，渲染引擎并不着急去执行下一个宏任务，而是执行当前宏任务中的所有微任务，因为 DOM 变化的事件都保存在这些微任务队列中，这样也就解决了实时性的问题。

MutationObserver 这个 API 就是上面的微任务的实现，关于这个 web API 具体可参考 MDN 的文档：https://developer.mozilla.org/zh-CN/docs/Web/API/MutationObserver

#### 6.2 如何处理单个任务执行时间过长的问题

因为所有的任务都是在单线程中执行的，所以每次只能执行一个任务，而其他任务就都处于等待状态。如果其中一个任务执行时间过久，那么下一个任务就要等待很长时间。

如果在执行动画过程中，其中有个 JavaScript 任务因执行时间过久，占用了动画单帧的时间，这样会给用户制造了卡顿的感觉，这当然是极不好的用户体验。针对这种情况，JavaScript 可以通过回调功能来规避这种问题，也就是让要执行的 JavaScript 任务滞后执行（异步）。

### 7、总结

- 如果有一些确定好的任务，可以使用一个单线程来按照顺序处理这些任务，这是第一版线程模型。
- 要在线程执行过程中接收并处理新的任务，就需要引入循环语句和事件系统，这是第二版线程模型。
- 如果要接收其他线程发送过来的任务，就需要引入消息队列，这是第三版线程模型。
- 如果其他进程想要发送任务给页面主线程，那么先通过 IPC 把任务发送给渲染进程的 IO 线程，IO 线程再把任务发送给页面主线程。
- 消息队列机制并不是太灵活，为了适应效率和实时性，引入了微任务。
