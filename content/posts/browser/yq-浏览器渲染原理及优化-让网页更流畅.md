依据上篇文章中我们讲到的 RAIL 模型，可以保证这样的用户体验下，那么网页就可以说是流畅的。

从一个常见的例子出发，用户点击侧边栏的按钮后侧边栏缓缓的弹出。整个用户的体验模型如果满足上述的条件，那么整个体验就是流畅的。

## 1、像素管道

当我们在点击网页的时候触发的一系列变化的流程，比如你用 JS 改了 DOM 某个节点的颜色和宽度，随后浏览器就会做样式计算，浏览器还会做布局、绘制，合并图层等，这个过程叫做像素管道。

现在 Vue、React 框架大行其道，当我们交互的时候其实就会执行一段 JS 代码，这个过程 JS 会改变 DOM 结构或者 CSS 样式，这样我们需要重新进行样式的计算(Style)，之后走后面的管道流程。

依据操作的流程可以分为三种情况：

- JS 改变某个节点元素的宽高或者边距，此时进行 Style 计算后，会重新布局(重排) — 绘制(重绘) — 图像合成
- JS 改变某个节点元素的背景颜色等，进行 Style 计算后，并不需要重新布局，只用绘制 — 图像合成
- JS 进行 transform 操作的时候，并不需要重新布局和绘制，仅仅只是图层的移动，就走图像合成的逻辑就好了

知道了上面的情况，我们进行优化的时候，就可以尽可能的去避免 Layout 和 Paint 操作，减少管道的过程来优化体验，具体改变那些样式触发怎么样的过程我们可以参考这个网站 https://csstriggers.com

## 2、JS 优化

按照之前的用户主动交互原则，用户点击后给他的回馈时间最好小于 100ms，但是我们知道 JS 是单线程的，如果一个 JS 执行的时间过长，那么就会影响后面的渲染过程，因而保证用户主动交互的流畅就需要避免长任务。

### 2.1、Web Worker

HTML5 规范中的 Web Worker 标准，简单而言就是我们可以将计算密集型的任务放到新的线程去执行，这样就不会阻塞主线程的执行。但是缺点是 Worker 线程没法操作 DOM，这点我们也很好理解，要是两个线程同时可以操作 DOM 就会导致冲突。

Worker：https://developer.mozilla.org/zh-CN/docs/Web/API/Worker

### 2.2、Time Slicing

如果你的任务就是要执行时间超过 100ms，且又要去操作 DOM，那么 Worker 也解决不了。这个时候我们可以将一个长任务切割成多个短的任务，这其实就是时间切片。

结合我们之前写到的生成器 Generator，我们可以中断函数的执行，回交主控制权给浏览器，这边直接看的是 Berwin 写的一段代码：

```javascript
function block() {
  ts(function*() {
    const start = performance.now()
    while (performance.now() - start < 100) {
      console.log(11)
      yield
    }
    console.log('done!')
  })
}

setTimeout(block, 5000)

function ts(gen) {
  if (typeof gen === 'function') gen = gen()
  if (!gen || typeof gen.next !== 'function') return
  (function next() {
    const res = gen.next()
    if (res.done) return
    setTimeout(next)
  })()
}
```

上面这段代码主要是当我们执行任务的时候，如果时间超过 100ms，我们就会暂停程序的执行，通过 setTimeout 将剩下需要执行的程序推到下一个宏任务队列中去排队让剩下的任务执行。

## 3、动画优化

我们知道用户在看一张轮播图或者一些切换的动画的时候，为了保证流畅性我们需要每 16ms 更新一帧动画到屏幕上，为了保证总的时间在 16ms 以内，我们需要保证的事情就是上面的管道渲染时间控制在 10ms 以内，因为浏览器去执行渲染也是需要预留一些时间的。

同时为了保证动画的流畅性，也就是不丢帧，我们应该使用 requestAnimationFrame 去执行我们的回调函数，使用它触发函数可以保证函数在每一帧的最开始执行，同时只要我们保证函数总体时间在 16.7 毫秒以内。

## 4、避免强制同步布局

前面的两个过程可以说都是在用户交互层面(避免长任务、动画)去优化的，这里将接着说道管道布局后面的优化。

其实像素管道的每一步都是异步的，JS 改了样式，它是异步的去计算样式、布局、绘制、图层合并，这里每一步都是异步的，也就是并不是等 JS 代码都执行完了才去执行后面的操作的。

有时候不小心就会出现强制同步布局，举个例子：第一行代码是设置一个元素的宽度，第二行代码是获取元素的宽度，仔细思考一下会发现第一行代码设置了元素的宽，但其实布局操作是异步的，我执行第二行代码的时候，浏览器还没有进行布局，那么当我的第二行代码想去获取宽度的时候，就必须在此刻先做一次布局，这个时候布局就是同步的。如果上述的例子在一个循环中去执行就会导致不断的去触发同步布局。

## 5、绘制与图层优化

前面的文章说过图层合成就是和 PS 图层一样，图层最大的特点是如果只是图层的位置变了，元素大小和内容没变，那么浏览器只需要重新去合成一下，就可以得到一个新的图。

比如我们有这样的一个操作，要把左边的块移动到右边；如果使用绘制的话，就需要将左边的图擦掉，经过布局的操作后再右边重新绘制一份。但是我们可以通过添加一个图层的操作去取消布局和绘制这个流程，图层的原理就是：图层在不停的变，浏览器通过合并图层就可以实现方框移动的效果。这个过程不需要绘制的。

## 附：RAIL - 以用户为核心的性能模型

如果判断一个网页的交互过程是否是流畅的，我们需要一个标准来帮助我们去判断。

Chrome 团队提出了一个以用户为中心的性能模型被称为 RAIL，它为工程师提供了一个标准，达到目标的网页用户就会觉得流畅；它将用户体验拆解为一些关键的操作，比如：点击、加载动画，并为这些操作规定一个目标，比如点击一个 button 之后，多长时间内反馈给用户会觉得流畅。

RAIL 将影响性能的行为划分为四个方面，分别是：Response（响应）、Animation（动画）、Idle（空闲）与 Load（加载）。

### 1、响应 Response

当用户点击了一个按钮之后，你需要保证在用户察觉出延迟之前就给出反馈。如果没有在合理的时间内完成响应，也就是采取动作和得到响应之间出现了断层，用户将会察觉到这个延迟。而这个时间临界点是 100ms。

要得到响应式的回应，我们需要：

- 在首次收到输入时，在 100 毫秒内得到回应
- 理想情况下，收到的回应就是最终结果。但如果最终结果还需要花更长的时间得到，那也要给用户一个"加载中"的标识，或是颜色的变更，告诉用户"本产品已经接收到了指令，还在处理中"，不至于让用户自我怀疑

### 2、动画 Animation

动画在交互中的应用是十分的普遍的，现在大多数设备的刷新频率在 60Hz，也就是每秒钟屏幕刷新 60 次。

网页动画的运行速度只要达到 60FPS，我们就会觉得动画很流畅。F（Frames）P（Per）S（Second）指的画面每秒钟传输的帧数，60FPS 指的是每秒钟 60 帧；换算下来每一帧差不多是 16 毫秒。

通常浏览器需要花费一些时间将每一帧的内容绘制到屏幕上（包括样式计算、布局、绘制、合成等工作），所以通常我们只有最多 10-12 毫秒来执行 JS 代码，要不就会出现卡顿或者掉帧的情况。

### 3、空闲 Idle

我们知道我们浏览网页不是一直都处于交互状态需要去渲染网页的，大部分时间浏览器是处于空闲的状态。通常我们会利用浏览器的空闲周期做一些低优先级的事情。requestIdleCallback 这个 API 就是利用浏览器空闲时间去处理事情，如 Intersection Observer 就是利用了浏览器空闲时间去检测元素是否在可视区域内。

RAIL 规定，空闲周期内运行的任务不得超过 50ms，当然不止 RAIL 规定，W3C 性能工作组的 Longtasks 标准也规定了超过 50 毫秒的任务属于长任务，那么为什么是 50ms 呢？

浏览器的 UI 线程是单线程的，这意味着同一时间主线程只能处理一个任务，如果一个任务执行时间过长，浏览器则无法执行其他任务，用户会感觉到浏览器被卡死了，因为他的输入得不到任何响应。

为了和前面达到 100ms 内给出响应，将空闲周期执行的任务限制为 50ms 意味着，即使用户的输入行为发生在空闲任务刚开始执行，浏览器仍有剩余的 50ms 时间用来响应用户输入，而不会产生用户可察觉的延迟。

事实上，不论是空闲任务还是高优先级的其他任务，执行时间都应该不超过 50ms，因为我们必须给用户的交互响应去预留时间。

### 4、加载 Load

如果不能在 1 秒钟内加载网页并让用户看到内容，用户的注意力就会分散。用户会觉得他要做的事情被打断，如果 10 秒钟还打不开网页，用户会感到失望，会放弃他们想做的事，以后他们或许都不会再回来。

因而我们需要将最有意义的内容先加载出来，将所有不需要在加载时处理的任务延迟到浏览器空闲时再处理（或根据需求懒加载）。接着页面要持续响应用户，绝对不允许出现在滚动页面、轻触或者看动画的时候卡顿。特别是当多个页面使用同一个线程的时候，要实现这样的目标真的不容易。
