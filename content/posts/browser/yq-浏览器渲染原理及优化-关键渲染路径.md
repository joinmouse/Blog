当浏览器从服务端接收到一个 HTML 页面的请求时，屏幕上渲染出来要经过很多个步骤。浏览器完成一系列的运行完成渲染到我们可视的内容通常称之为"关键路径渲染"(Critical Rendering Path)。

理解 CRP 相关的知识可以帮助我们更好的提供网站的性能，主要分为以下几个部分：

- 构建 DOM 树
- 构建 CSSOM 树
- 运行 JS
- 创建 Render 树
- 生成布局 Layout
- 绘制 Paint
- 合成图像 (Composite)

## 2、将 CSS 转化为 CSSOM

CSS 转化为 CSSOM 的处理过程和 HTML 有些类似，只不过是 CSS 而不是 HTML。CSS 字节转化为字符，经过上述的过程，最终生成 CSSOM 树的结构。

body 节点的子节点继承了 body 的样式规则(font-size: 16px)，这就是 CSS 为啥称之为层叠样式表。

注：HTML 可以逐步解析，它不需要等待所有 DOM 都构建完毕后再去构建 CSSOM，而是在解析 HTML 构建 DOM 时，若遇见 CSS 会立刻构建 CSSOM，它们可以同时进行。

然而 CSS 需要完整的构建，不完整的 CSS 是无法使用的，因为 CSS 的每个属性都可以改变 CSSOM，所以会存在这样一个问题：假设前面几个字节的 CSS 将字体大小设置为 16px，后面又将字体大小设置为 14px，那么如果不把整个 CSSOM 构建完整，最终得到的 CSSOM 其实是不准确的。

因而必须等 CSSOM 构建完毕才能进入到下一个阶段，哪怕 DOM 已经构建完，它也得等 CSSOM，然后才能进入下一个阶段。所以 CSS 也被认为是"渲染阻塞资源"。

## 3、运行 JS

我们都知道 JavaScript 的加载、解析与执行会阻塞 DOM 的构建，也就是说，在构建 DOM 时，HTML 解析器若遇到了 JavaScript，那么它会暂停构建 DOM，将控制权移交给 JavaScript 引擎，等 JavaScript 引擎运行完毕，浏览器再从中断的地方恢复 DOM 构建。因而 JavaScript 也被认为是一个"解析器阻塞资源"。

同时 JS 可能会改变 DOM 结构，但 JS 无法获取到 JS 后面的元素，因为 DOM 还没有构建到那边。JS 对关键路径渲染的影响不只是阻塞 DOM 构建，也会导致 CSSOM 阻塞 DOM 构建，这是为什么呢？

原本 DOM 和 CSSOM 的构建是互不影响，但是一旦引入了 JavaScript 之后，JS 如果需要去更改 CSSOM。前面我们说过了不完整的 CSSOM 是无法使用的，但是 JS 想去访问 CSSOM 并更改它，那么在执行 JS 前，我们就需要拿到完整的 CSSOM。这样就导致了一个情况：如果浏览器尚未完成 CSSOM 的下载和构建，而我们却想在此时运行脚本，那么浏览器将延迟脚本执行和 DOM 构建，直至其完成 CSSOM 的下载和构建。

换句话说在这种情况下，浏览器会先下载和构建 CSSOM，然后再执行 JavaScript，最后在继续构建 DOM。这样就会导致严重的性能问题。

## 4、创建 Render 树

Render 树是 DOM 和 CSSOM 的组合，这个树代表了页面最后的呈现。

渲染树的重要特性是它捕获可见的内容，有些节点被 CSS 隐藏在渲染树中就会被忽略，如 `p > span` 节点就不会出现在渲染树中，因为该节点设置了 `display:none` 的属性。

对于每个可见的节点，都会为其适配 CSSOM 规则并应用它们。

## 5、布局 Layout

有了渲染树之后，接下来就会进入布局阶段，就是浏览器依据你的各个节点在页面中确切的位置和大小，通常这一行为也被称为"自动重排"。

布局流程就是输入一个"盒模型"，它会精确地捕获每个元素在视口内的确切位置和尺寸，所有相对测量值都将转换为屏幕上的绝对像素。

## 5、绘制 Paint

当布局完成的时候，光栅器就会执行绘制操作(类似 canvas 画布的绘制过程)，去填充页面的像素。

## 6、合成图层 Composite

我们知道 PS 里面的一张图片是有多个图层合成的，其实网页也是一样的，当绘制完成之后，就会将多个绘制的图层进行合并，最终现在在我们浏览器屏幕上的就是合成后的网页，通过 Chrome 的工具我们可以看到这样的视图结构。
